# LLM Integration Profile / Consumer Kit — Block D Change Report

Date: 2026-08-13
Status: Block D complete; stop before slim external deployment.

## BEFORE Block D

Public `llm_integration_profile/v1` and Consumer Kit already existed, but Knowledge Assistant still had two private integration remnants:

- `GroundedAssistant.system_prompt()` independently assembled scope/tool JSON around the reusable policy;
- `KnowledgeApiAssistantTools` contained a second procedural `tool -> HTTP endpoint/request` dispatch implementation.

`get_knowledge_context` also remained as an Assistant-only synthetic tool even though the same scope/capabilities/artifacts were embedded in the public Integration Profile.

## AFTER Block D

`knowledge-integration 0.1.1` remains the single owner of reusable integration semantics:

- canonical tool catalog and capability gating;
- retrieval profiles and consumer-neutral grounding/evidence/gap policy;
- declarative Knowledge API bindings;
- deterministic `tool + pinned scope + arguments -> HTTP request` materialization;
- typed `llm_integration_profile/v1` and deterministic renderers.

`knowledge-assistant 0.25.1.post6` is now a reference consumer of that public contract:

- `GroundedAssistant` requires an explicit Integration Profile;
- its system prompt begins with the same public Integration Profile renderer used by Consumer Kit;
- only Assistant-specific action/dialogue protocol is appended locally;
- provider/model, conversation, max steps, retries and JSON action mechanics remain Assistant concerns;
- `KnowledgeApiAssistantTools` executes the canonical declarative HTTP request generated by `knowledge-integration` instead of owning product-specific endpoint methods;
- synthetic `get_knowledge_context` is removed from the Assistant tool surface because scope/capabilities/artifacts already exist in the Integration Profile.

`knowledge-api 0.30.5` has no runtime/read semantic change; version changes only align its dependency with `knowledge-integration==0.1.1`.

## Architecture

```text
                      ┌─ Knowledge Assistant reference consumer
Integration Profile ─┤
                      └─ External LLM / external agent
```

There is one tool/capability/retrieval/API-binding integration contract and multiple consumers.

## UCP + SQL + PDM parity

Using the recorded metadata from the real previously accepted UCP+SQL+PDM revision:

- 44 capabilities;
- 16 public capability-gated tools;
- Block C external Consumer Kit tool names and Block D Assistant tool names are identical;
- the public Integration Profile renderer is the exact prefix of the Assistant system prompt;
- Assistant-only control protocol is appended after the public contract;
- old private `TOOL_SCOPE_JSON` / `TOOL_CATALOG_JSON` assembly is absent;
- every exported binding declares expected response schema versions.

## Not done

- No prompt-recipe tuning.
- No LLM answer-quality optimization.
- No Core/Runner/KLC/Prepared Knowledge production changes.
- No compatibility adapter or dual tool mapping.
- Full framework regression was not run.
